# 精确矿量生成性能分析

本文记录 2026 年 8 月 7 日对精确矿量生成的热点分析、已实施优化、性能结果和后续方向。正确性基准仍为 `AGENTS.md` 记录的游戏版本与 `tests/fixtures/game/verts-200-game.bin`。

## 结论

原实现的主要问题不是矿脉放置，而是为每颗实体星球完整生成 precision 200 地形。完整网格包含 161,604 个顶点；矿脉放置实际只通过 `queryHeight()` 读取候选中心和节点附近的少量顶点。

生产路径现已改为按需计算高度：

- `queryHeight()` 只计算插值窗口内尚未缓存的顶点；
- 高度缓存使用 generation stamp，切换星球时不清空 161,604 项标记；
- 普通精确矿量不生成 `biomoData`，也不计算地形摘要；
- 完整地形、biome 和摘要仍由 parity oracle 显式生成；
- 同一星球反复使用的 `SimplexNoise` 排列表按线程缓存；
- ABI v2 对插件初筛通过的候选行星逐个生成精确汇总，不再在回调前计算整个星系。
- 按需模式继续使用 64 seed 分块，避免大范围扫描为每个 seed 预建调度项。

在两枚 64 星 seed 的计数样本中，共有 493 颗行星，其中 425 颗需要地形。完整生成需要计算 68,681,700 个顶点；按需路径只计算 376,643 个顶点，占 0.548%。

## 性能基线

测量环境：

- 编译器：MSYS2 UCRT64 GCC 16.1.0；
- 构建：Release、LTO、`-fno-fast-math -ffp-contract=off`；
- 输入：seed 0 和 1，64 星；
- 插件：隔离运行目录中的 `vein_amount_v2_test`；
- 顶点网格：`verts-200-game.bin`；
- 计时：CLI 内部 `ms used`，不包含构建时间。

| 模式 | 优化前 | 优化后中位数 | 提升 |
| --- | ---: | ---: | ---: |
| 1 线程，2 seed | 21,357 ms | 573 ms | 37.3× |
| 2 线程，连续 2 seed | 21,359 ms | 318 ms | 67.2× |

优化前的 2 线程结果与单线程接近，原因是固定 64 seed 分块把连续短区间交给了同一个 worker。表中的 2 线程优化后结果属于旧的全星系精算调度实验；ABI v2 改为候选行星按需请求后，不再为每个 seed 预建单独调度项。

### 按行星请求

2026 年 8 月 8 日复测同一组 seed。旧版 ABI v2 smoke 会为 493 颗行星生成汇总；新版插件先定位出生行星，每个 seed 只请求 1 颗，并在调用前后遍历星系，验证其他行星没有精确汇总。

| ABI v2 调用方式 | 1 线程，2 seed 中位数 | 进入精算的行星 |
| --- | ---: | ---: |
| 回调前生成整个星系 | 573 ms | 493 |
| 初筛后按单行星请求 | 12 ms | 2 |

该样本缩短约 47.8 倍。收益取决于初筛保留下来的行星比例；单颗行星的精算公式、随机消费和结果缓存没有改变。

## 热点分解

### 完整地形生成

每颗实体星球原先执行一次 `dispatchTerrain()`，遍历全部 161,604 个顶点。历史测量约为 58.1 ms/planet，是绝对热点。

矿脉放置不读取 biome。地形摘要也只用于校验工具。生产路径为这些诊断数据支付完整计算成本，没有必要。

### 重复噪声初始化

惰性计算初版按每次高度查询重新进入地形算法。两枚 seed 的计数为：

- `terrainHeightQueries`：171,482；
- `terrainSparseBatches`：162,134；
- `terrainVertexEvaluations`：376,643；
- `rngConstructions`：495,398。

多数重复构造来自相同地形 seed 的 `SimplexNoise`。排列表现在保存在每线程 8 项缓存中；缓存未命中时使用局部 shuffle，不再修改全局静态数组，也不再持有全局互斥锁。

### 节点高度查询

算法 7 的节点接受条件恒为真；`waterItemId == 0` 时，其他算法的节点接受条件也不读取高度。此类节点不再调用 `queryHeight()`。随机数消费、节点顺序和矿量累加顺序不变。

### 调度粒度

旧版在声明 `NeedsVeinAmounts` 后必然精算整个星系，因此使用单 seed 分块平衡重负载。按需接口下，大量 seed 可能只执行廉价初筛；继续使用单 seed 分块会为大范围扫描创建近似一项／seed 的 `seedBlocks`，并增加原子调度次数。当前恢复 64 seed 分块，精算成本由多个区块自然分散；如果后续观测到候选密度导致明显负载偏斜，再改为不预物化的自适应调度。

## Bit 级一致性

按需计算只改变纯地形顶点的求值集合，不改变以下顺序：

- `DotNet35Random` 的构造、调用次数和调用顺序；
- 矿簇中心拒绝采样顺序；
- 已接受矿簇的碰撞检查顺序；
- 节点扩张与去重顺序；
- 节点数量和基础矿量的累加顺序；
- 每个顶点公式内部的运算顺序和窄化位置。

每个地形顶点只依赖顶点坐标、算法参数和初始化完成的噪声排列表。顶点之间没有数据依赖，也不在顶点循环内消费随机数，因此按索引延迟求值不会改变该顶点的位模式。

完整校验模式仍生成全部 `heightData` 和 `biomoData`。普通生产模式只生成矿脉逻辑实际读取的高度；`TerrainDigest` 为空，直到调用方显式请求完整诊断。

生产 CLI 在精确模式启动前加载并校验捕获网格。搜索顺序为：

1. `DSP_VERTS200_PATH`；
2. `Prototypes/verts-200-game.bin`；
3. 源码树中的 `tests/fixtures/game/verts-200-game.bin`。

文件大小或 FNV-1a 指纹不匹配时，CLI 拒绝启动精确矿量生成，不再静默使用无法与 Unity 逐位一致的重建网格。

## 后续 CPU 优化

当前实现仍会为每个 sparse batch 重新进入算法函数。后续可把每个算法的循环前状态提取为 `TerrainEvaluator`，每颗星球只初始化一次噪声对象、圆形或椭圆参数，再按索引调用纯 `sampleHeight()`。这可以消除 162,134 次重复分派和排列表复制，但改动范围明显大于本轮方案。

次要方向包括：

- 复用矿簇和节点的临时 `std::vector`；
- 复用 `VeinAmountSummary` sidecar；
- 共享只读 precision 200 顶点和索引表，降低高线程数下的内存占用。

这些优化必须继续通过完整游戏参照验证，不能只比较最终总矿量。

## GPU 方向

矿脉放置不适合迁移到 GPU。候选中心是否接受会决定后续随机数消费；已接受中心、节点扩张和去重也依赖前序结果。并行重排会改变最终节点顺序或数量。

地形顶点计算具备数据并行性，但普通矿量路径目前只访问完整网格的约 0.55%。在该负载下，把 161,604 个顶点全部提交给 GPU 会计算约 182 倍的非必要顶点，并承担任务提交和回传成本。GPU 更适合完整地形摘要、批量地形导出或覆盖率显著提高的负载。

权威 GPU 后端还需要解决混合 `double`/`float` 语义、显式窄化、FMA 收缩、denormal、除法、平方根和超越函数差异。设备 `sin`、`cos`、`pow`、`asin` 不能直接视为与 Mono/CPU libm 逐位一致。

可研究的受限方案是：

1. CPU 完成全部随机初始化和算法参数准备；
2. GPU 只执行经过审计的基本算术和 SimplexNoise；
3. CPU 保留所有影响阈值判断的超越函数，或使用逐位验证过的软件实现；
4. 对每种 GPU、驱动和 kernel 哈希运行完整 `heightData`、`biomoData`、节点和矿量参照；
5. 未认证环境自动回退到 CPU。

在完成一次性 `TerrainEvaluator` 初始化之前，不建议投入 GPU 后端实现。
