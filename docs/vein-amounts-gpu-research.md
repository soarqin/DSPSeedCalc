# 精确矿量生成的 GPU 可行性

## 结论

当前实现不引入 CUDA、OpenCL 或其他 GPU 运行时。精确矿量结果以 CPU 实现为权威来源。最新热点数据、CPU 优化结果和 GPU 实施顺序见 `docs/vein-amounts-performance.md`。

地形高度计算是唯一适合批量并行的部分，但当前参考实现混合使用 `double`、Unity `float`、超越函数、显式窄化和 `ushort` 截断。不同 GPU、驱动和着色器编译器不能默认保证与 Mono/CPU 相同的位级结果。矿脉放置还包含串行 `DotNet35Random`、拒绝采样和顺序相关的簇碰撞检查，并行执行会改变随机数消费和对象顺序。

生产路径已经改为按 `queryHeight()` 需要的顶点惰性计算。两枚 64 星 seed 的计数样本只访问完整网格的约 0.55%。因此，GPU 满网格计算当前会执行大量非必要工作；应先完成 CPU evaluator 状态复用，再重新测量 GPU 的剩余收益。

## 地形阶段

每个球面顶点的噪声计算大体独立，因此可以批量提交给 GPU。不过，下列因素阻止其直接用于权威结果：

- `System.Math` 双精度运算与 Unity `Mathf` 单精度运算交错；
- `Sin`、`Cos`、`Pow`、`Sqrt`、`Asin` 等函数的设备实现可能产生不同末位；
- 算法要求保留 `double -> float -> double` 转换点；
- `heightData` 写入依赖窄化和截断结果，微小误差可能改变地形高度及后续矿点筛选；
- 算法 `10` 等实现包含严格的运算顺序和更新后变量依赖，不适合代数重排。

## 矿脉阶段

矿脉生成不适合直接并行化。候选中心的接受与否会影响后续随机调用、簇之间的距离判断和最终节点顺序。即使把候选批量生成到 GPU，也必须由 CPU 按原顺序重新判断，无法省去主要的串行工作。

## 可接受的后续实验

后续可以测试 GPU 地形预计算，但只能作为非权威实验：

1. CPU 完成全部随机初始化和算法参数准备；
2. GPU 只执行经过审计的基本算术和 SimplexNoise；
3. CPU 保留影响阈值判断的超越函数，或使用逐位验证过的软件实现；
4. 对固定 seed 的完整 `heightData`、`biomoData`、节点数和基础矿量进行逐位比较；
5. 任一设备、驱动或 kernel 哈希出现差异时，丢弃 GPU 结果并回退到 CPU。

在 GPU 结果能够跨设备稳定匹配之前，不应通过插件 API 或 CLI 暴露为「精确矿量」。
